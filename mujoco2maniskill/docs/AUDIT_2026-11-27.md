## 1. Generated-program isolation

What was there. `m2m/api.py check_program` allowed a private attribute on any name called `self` or `cls`, and a
program was executed in the simulator's process with a robot object whose calls are closures over the real robot.
A program the check accepted could therefore do `self = robot.move; self.__closure__[i].cell_contents` and reach
`X5Robot.env`, i.e. every true pose. The allowed libraries also carry `os` and `sys` (`cv2.os`, `cv2.sys`) and
file readers the name list did not have (`numpy.fromregex`), so a program could read any file the harness's user
can read (a scene file with the true positions is named on the episode's command line).

Reproduced (`tests/test_boundary.py`, dummy robot with a `secret`, a temporary canary file): the three programs
pass the old check; run in-process they print the secret and the file's content twice.

Fix. Agent-written code runs in a bubblewrap sandbox (the project's recipe, `execution/sandbox.py _base`): no
network, the system and the Python environment read-only, nothing of the repository, the experiment's records or
the home directory, no writable file (RLIMIT_FSIZE 0), a memory ceiling. Its robot is a socket: the host answers
only the documented calls (look, state, move, turn, home, wait, time_s, set_gripper, segment, show); messages are
JSON plus numpy arrays in .npy form, never pickle. A practice-world file runs in a sandbox of its own: `scene()`
returns its scene dict, `success(state)` asks the host for the documented state queries of its own practice world.
Applied in `xsim/bi/target_run.py`, `xsim/bi/practice_run.py` (program and world), `sweep_blocks/run_program.py`
and `run_episode.py` (the one-arm target). The syntax check is tightened too, and documented as a first line only.
Not changed: the one-arm PRACTICE path, which is the main project's (`src/agentic_robotics/bimanual/practice.py`,
outside this folder): it sandboxes the whole episode, simulator and program in one process, so files and network
are closed there but the true state is not.

Runner equivalence, as far as it was tested (it is established on these scenes, not in general): the same program
on the same scene gave identical results and identical logs with the old in-process runner (run twice) and the
sandboxed one, on two target development scenes (D's final program of the first run), one practice scene without
segmentation, and one insertion scene of the one-arm rig; and every judged success of the first run, replayed with
the sandboxed runner (section 5), reproduced the historical episode's success, robot time, number of commands and
number of segmentation calls. Episodes that failed were not replayed. The re-evaluation of every compared final
program under the fixed runner (planned for when the running sessions have ended) is the full comparison.

Were completed runs affected? No exploitation was found in the inspected artifacts. That is a statement about what
was inspected, not a guarantee that exploitation was impossible: the holes were open while those runs were made.
Inspected: every saved program version and world file, by a scan of their syntax trees
(`audit_data/code_audit.py`): 88 program files (73 distinct) and 49 world files (17 distinct) of the first run and
the initialization, 25 programs and 4 world files of the running second run. None uses a private or dunder
attribute, none assigns `self` or `cls`, none takes an attribute of the robot outside the documented list, none
reaches `os`, `sys` or a file function; imports are math, numpy, cv2 and `scipy.optimize.linear_sum_assignment`
only. The tightened check refuses none of them. Limits of this inspection: it reads attribute syntax and imports,
so access built at run time would not show in it (the ways to do that without attribute syntax are `getattr`,
which the old check refused, and `operator.attrgetter` / `methodcaller`, and no saved file imports `operator`); it
reads the saved versions, which is all the harness ever ran (practice and target runs take a saved version); and
the file-tool calls of the sessions' transcripts were checked separately (none outside a workspace was answered).
What it cannot show: that no other route exists that nobody has thought of.

## 2. Forks and stale results

What was there. `fork_root.py` copied `private/` whole except `candidates/`: with it `private/rounds/B|C|D/round_0..4`,
the hidden side of the first run's target submissions (445 MB). The batch runner read `result.json` from an
episode's folder whether or not the new process had written it.

What that could do. A session's feedback and its counted successes come from the PUBLIC payload folder, which is
always new (`rounds/round_k/` is made with `mkdir()`): an old private result could not turn into a success shown to
an agent. It could enter the private record (`private_round.json`) of a submission whose process failed, and it
could enter a held-out evaluation written into an existing folder.

Fix. Results carry the id of the execution that wrote them, with the program's and the scene's hashes; a batch
runner takes a result only with its own id and writes only into folders that did not exist; a submission is
refused before it is counted if its private folder exists. A fork copies the frozen scene sets by an allow-list.
`check_bi.py` copied `private/` whole as well: fixed the same way. Regression (`tests/test_provenance.py`): an old
successful result, then a failed execution -> a failure with the harness's error, the old file renamed aside.

Audit of the 10 x 10 root (`audit_data/stale_audit.py`, sessions running): for every target episode of every
submission made so far, every accepted result was written after its session started; no process failure; no result of the
first run was taken. 1,291 files of the first run (videos, frames, images) lie in the same episode folders as the
new ones (rounds 0 to 4, episodes 0 to 4 of each condition): distinguishable by their modification time, earlier
than the session's start. The folders of rounds the sessions have not reached yet still hold the first run's
`result.json` files. Not moved: the records are as they were (moving the unused copies aside was not permitted
without the user's word).

## 3. Mirrored OOD generation

Confirmed in `backend.prepare`: a fresh preparation sent every non-appearance OOD split through `variant()`, which
knows cube size, mass and friction only; `ood_mirrored` would have come out unmirrored under that name. That path
was never run for it: the existing split was made by the later-added path, which mirrors. Fix: one routine
(`make_split`) for both paths; `variant()` refuses a change it does not make. Tests check positions and
orientations (x -> -x; (w, x, y, z) -> (w, x, -y, -z), i.e. S R S for S = diag(-1, 1, 1); the mouth's direction; an
involution), and that a fresh and a later-added preparation make the split with the same seed and way.

The existing `test_private/ood_mirrored`: all 30 scenes and all 96 candidates are mirrored (brush right of the
dustpan, mouth towards -x, cubes left), and each scene's un-mirrored image is a scene of the generator's family.
No corrected split is needed. (Found on the way: the mouth is within about 20 degrees of +x, not 15 as written.)

## 4. Final-evaluation caching and provenance

What was there. `final()` copied the final program once to `final_eval/<cond>/program.py` and reused it and every
`results.json` found, without comparing anything. A later change of the session's final program, of the evaluator
or of a scene would have gone unnoticed.

Fix. A record per (program hash, evaluator hash, scene-set identity): `final_eval/<cond>/<split>/eval_<key>/` with
`evaluation.json`; reused only if complete and all three match; the split's frozen manifest is checked before
anything runs; nothing is written into an existing record; the summary of bound records is `summary_bound.json`
(the old `summary.json` is not touched). The evaluator's provenance now covers every local file the episode runner
imports (21), the robot's and objects' assets (126 files), the versions of the simulator's packages, and the
segmentation service's configuration (its weights are not ours to hash; the GPU and driver are recorded, not hashed).

Existing results (`out/xsim/sweep_blocks/rep0/final_eval`, 20 evaluations = 4 conditions x 5 splits):
for each condition the evaluated program is byte for byte the session's selected final version; each split's
scenes match their frozen manifest and are in the split's order; every result was written after the program was
frozen and after the evaluator's last change (03:06); the evaluator hash recorded at every development submission
equals the hash of the files now; no process failure. No mismatch.

## 5. Judge versus stated task

Exact semantics (`sweep_blocks/env.py info`, written out in `sweep_blocks/judge_strict.py`): a cube is inside if
its centre, seen from above, is in one of the pan's support circles or over the handle's rectangle (no height, no
contact, no speed); the conditions are tested after every action and the episode ends at the first instant they
all hold (no settling interval); only a two-finger squeeze of more than 1 N for three actions is ruled out (a push
with a closed gripper, an arm or the pan is allowed); nothing is asked of where the brush lies beyond its origin's x.
The task text given to the sessions states these same conditions.

Did any measured success differ from the intended task? Every judged success of the first run (held-out and
development) was examined twice.
- From the private logs (`audit_data/judge_audit.py`): every cube's centre is at a height that fits the pan's floor
  or ramp at the success, and none had moved in the last second before it.
- By replay with contacts recorded and the simulation run on for 1 s (`judge_strict.record`): every replay
  reproduces the historical episode exactly (success, robot time, commands, segmentation calls); in every one the
  conditions hold through the interval and every cube rests in the pan. In some of them a robot link (a finger of
  the gripper that holds the brush) pressed on ONE cube for a fraction of a second, on the table before it reached
  the pan; that cube moved less during the contact than while the brush was touching it. No success was made by
  pushing the cubes in with a gripper in place of the brush.

The original judge stays the experiment's definition of success: nothing below replaces a score. Two separately
named SENSITIVITY ANALYSES of its successes (`sweep_blocks/judge_strict.py`):
- **settled-and-resting**: the judge's conditions still hold 1 s after the success, with the robot commanded to stay,
  and every cube then rests in the pan (slower than 10 mm/s, its lowest face 2 to 20 mm above the table);
- **no-robot-contact**: before the success no link of either arm pressed on a cube with more than 1 N for 3 actions
  running. As written it also counts a brief contact of the fingers that hold the brush; it does not mean "the cube
  was pushed in by the gripper".

The counts per condition, the list of the contact cases and the description of one marginal success in the mirrored
split are held-out outcomes: they are in the local evidence archive (`out/audit_2026-11-27/`, never committed),
not in this repository.

## 6. Settings, reporting, README

- `xsim/configs/`: the two experiments as named settings with the initialization budgets; they equal what the
  sessions' manifests recorded.
- `launch.ending` / `split_summary`: an episode the judge ended on a success ("time: the episode is over") was
  counted with the timeouts. No reported number was affected: every development and held-out episode of the
  first run ended "returned".
- README: the stale parts rewritten (two-arm task, settings, boundary, provenance, tests, machine path).
- The live spending figure left out the output tokens (fixed on the workstation at 11:26, before the 10 x 10
  sessions started; within 1.1 % of the CLI's totals on the five finished sessions).

## Found on the way

- Practice episodes that use the segmentation service are not reproducible: the same program, world and seed
  gave different segmentation scores and different outcomes in three runs. Without
  segmentation the practice episode was identical run to run; target episodes with segmentation were identical.
- `launch.final(splits=...)` dropped the other splits from `summary.json` (fixed on the workstation at 11:26; the
  summary was rebuilt from the stored results, unchanged).

## What needs rerunning

Nothing for correctness, and no paid session. Decided by the user on 2026-11-27: when the running sessions have
ended, every compared final program (A included) is evaluated again under the fixed runner, on the same held-out
scenes and with the original judge, into new hash-bound records; the historical results are kept as they are, and
no held-out outcome goes back to an agent.
